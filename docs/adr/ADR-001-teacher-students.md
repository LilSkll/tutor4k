# ADR-001: Почему отдельная таблица `teacher_students`

- **Status:** Accepted
- **Date:** 2026-08-01
- **Module:** Teacher Dashboard

## Context

Нужна связь «преподаватель ↔ ученик» в рамках курса, с возможностью групп, школ и смены преподавателя. Рассматривались варианты:

1. Колонка `profiles.teacher_id` (ученик «принадлежит» одному учителю).
2. Массив / jsonb со списком учителей на профиле ученика.
3. Отдельная таблица связей (enrollment / link).

## Decision

Вводим таблицу **`teacher_students`** как единственный источник правды о связи:

| Поле | Назначение |
|------|------------|
| `teacher_id`, `student_id` | участники связи |
| `course_id` | связь и статистика только в рамках курса (spanish / english) |
| `group_id` | опционально группа |
| `role` | `student` \| `trial` \| `alumni` (`observer` — позже) |
| `status` | `pending` \| `active` \| `revoked` |
| `created_by` | `teacher` \| `school_admin` \| `system` — кто создал связь |
| `deleted_at` | soft delete (`NULL` = живо) |

Доступ преподавателя к данным ученика разрешён **только** при active-связи (после authz в Teacher API).

## Consequences

**Плюсы**

- Ученик может учиться у нескольких преподавателей и по разным курсам.
- Смена преподавателя = новая/отозванная связь, без миграции `profiles`.
- Готовность к иерархии Школа → Преподаватель → Группа → Ученики.
- Аудит происхождения связи через `created_by`.

**Минусы**

- Каждый teacher-read требует проверки join/`assertCanViewStudent`.
- Нельзя «просто» читать прогресс по `profiles.teacher_id`.

## Rejected alternatives

- **`profiles.teacher_id`:** один учитель навсегда; ломает школу и смену педагога; смешивает identity и enrollment.
- **JSONB на профиле:** слабые ограничения целостности, неудобный RLS/уникальность по курсу.
